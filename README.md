# Перенос CRM из облачного Bitrix24 в коробочный

Архив собран под фактическую выгрузку `data/bitrix24_export.xlsx` и текущую структуру коробки. Он **не переносит всё подряд**. В него включены только данные, необходимые для CRM:

- 9 пользователей, которые реально являются ответственными в карточках;
- 601 компания;
- 441 контакт;
- 4 существующих лида;
- 1443 облачные сделки с преобразованием под новую модель;
- связи компания–контакт, лид–контакт и сделка–контакт;
- реквизиты и адреса компаний/контактов;
- три нужных пользовательских поля.

Не переносятся задачи, проекты, рабочие группы, таймлайн, дела, смарт-процессы, файлы и товары. В выгрузке товаров нет, а остальные блоки не относятся к текущей задаче.

## Как преобразуются карточки

В коробке менеджер работает в лиде до андеррайтинга, поэтому облачные сделки распределяются так:

| Этап облачной сделки | Объект и этап в коробке |
|---|---|
| Новая | Лид — Новый лид |
| В работе | Лид — Квалификация |
| Поиск данных / контактов | Лид — Недозвон / поиск контакта |
| Требуется дополнительный звонок | Лид — Повторный контакт |
| Ожидание действия клиента | Лид — Повторный контакт |
| Согласование условий | Лид — Сбор данных |
| Сбор документов | Лид — Сбор данных |
| Андеррайтинг | Сделка — Расчёт / андеррайтинг |
| Договор подписан | Сделка — Договор подписан |
| Сделка провалена после андеррайтинга | Сделка — Сделка провалена |
| Сделка провалена до андеррайтинга или этап неизвестен | Лид — Некачественный лид |

Результат по текущему Excel:

- 1326 облачных сделок станут лидами;
- 117 облачных сделок останутся сделками;
- вместе с 4 существующими лидами ожидается 1330 лидов.

## Пользовательские поля

Настроено сопоставление:

1. Причина срыва облачной сделки  
   `UF_CRM_1779448756033` → поле лида коробки `UF_CRM_1785508658316`.

   Значения сопоставляются **по тексту**, а не по внутренним ID. Поэтому старые ID 386/388/... и новые 26/27/... не смешиваются.

2. Номер договора  
   `UF_CRM_1781611696235` → поле сделки коробки `UF_CRM_1785507415551`.

3. Детальная причина срыва  
   `UF_CRM_1781611791954` → поле сделки коробки `UF_CRM_1785508290845`.

Для карточек, которые превращаются из сделки в лид, детальная текстовая причина сохраняется в комментарии лида. Для проваленных сделок после андеррайтинга текстовое поле содержит и справочную причину, и детализацию.

**Первые два новых строковых поля коробки в предоставленном REST-ответе не содержали подписей. Сопоставление задано по порядку создания. Перед реальным импортом workflow `01 - Проверить план миграции` проверяет наличие и тип полей; при необходимости коды можно поменять в `config/migration.json`.**

## Пользователи

`config/users.csv` содержит только 9 сотрудников, на которых реально закреплены CRM-карточки. Скрипт:

- ищет пользователя в коробке по email;
- не создаёт дубль, если пользователь уже есть;
- пытается найти подразделение по названию;
- если подразделение не найдено, использует `default_department_id`, указанный при запуске workflow 02.

Приглашение через `user.add` отправляет пользователю стандартное письмо Bitrix24. Webhook должен принадлежать администратору и иметь scopes `user`, `department`, `crm`.

## Подготовка GitHub

1. Создайте **приватный** репозиторий. Excel содержит рабочие и контактные данные.
2. Загрузите в него содержимое архива.
3. В `Settings → Secrets and variables → Actions` создайте secret:

   `TARGET_BITRIX_WEBHOOK_URL`

   Значение — входящий webhook администратора коробочного Bitrix24.
4. Откройте вкладку Actions.

## Правильный порядок запуска

### 1. `01 - Проверить план миграции`

Ничего не создаёт. Проверяет:

- нужные статусы лидов и сделок;
- источник `Minerals E-Qazyna`;
- три целевых пользовательских поля;
- все 10 значений причины срыва;
- наличие пользователей по email;
- ожидаемые количества после преобразования.

Пока этот workflow не зелёный, реальный импорт не запускать.

### 2. `02 - Зарегистрировать нужных пользователей`

Сначала `mode = dry_run`. Затем `mode = apply` и подтверждение `INVITE_USERS`.

Если названия подразделений в коробке отличаются, заполните колонку `target_department_id` в `config/users.csv` либо укажите общий `default_department_id` при запуске.

### 3. `03 - Перенести CRM в коробку`

Рекомендуемый тест:

- `mode = apply`;
- `max_items = 10`;
- `confirm = IMPORT_TO_BOX`.

Проверьте 10 компаний, контактов, лидов и сделок. После проверки повторите с `max_items = 0`.

Повторный запуск не должен создавать повторные карточки: в комментарий каждой мигрированной сущности записывается техническая метка, по которой скрипт находит уже созданный объект.

### 4. `04 - Сверить результат миграции`

Считает технические метки и сравнивает их с ожидаемыми количествами.

## Отчёты

Каждый workflow сохраняет artifact с файлами:

- `actions.csv` — каждое действие;
- `errors.csv` — только ошибки;
- `maps.json` — соответствие старых и новых ID;
- `summary.json` — итоговые количества и проверки.

## Важные ограничения

- Исходные даты создания карточек REST-методами обычно не восстанавливаются как системные даты.
- Роботы и уведомления коробки могут сработать при добавлении карточек. На время миграции их нужно отключить либо ограничить.
- Скрипт переносит реквизиты и адреса, но банковских реквизитов в выгрузке нет.
- Для потерянной сделки без предыдущего этапа применяется безопасное правило: она становится некачественным лидом. Иначе пришлось бы выдумывать, проходила ли она андеррайтинг.

### Различие одного значения справочника

В облаке значение называется `Уже работает с конкурентом`, а в коробке — `Уже работают с конкурентом`. Это отличие уже внесено в `value_aliases`, поэтому 282 заполненных значения не потеряются.

## Запуск на Windows self-hosted runner

Эта версия workflow рассчитана на локальный runner с метками `self-hosted`, `Windows`, `X64`.
Окно `run.cmd` должно оставаться открытым и показывать `Listening for Jobs`.
Python должен быть доступен командой `python` из PowerShell.

Порядок первого безопасного запуска:
1. `01 - Проверить план миграции`.
2. `02 - Зарегистрировать нужных пользователей` с `mode=dry_run`.
3. `03 - Перенести CRM в коробку` с `mode=dry_run`, `max_items=10`, `allow_user_fallback=false`.
4. После проверки отчётов — реальные режимы `apply`.
