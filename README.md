# Быстрая инвентаризационная выгрузка Bitrix24

Архив предназначен для аудита текущего облачного Bitrix24 перед переносом в коробочную версию. Скрипт работает только на чтение и формирует:

- JSON по каждой сущности;
- Excel для проверки данных и пользовательских полей;
- `manifest.json` с количеством строк и контрольными суммами;
- ZIP всего дампа;
- журнал выполненных и недоступных REST-методов.

## Исправление зависания первой версии

Первая версия вызывала метод `methods` как постраничный список. Этот метод может вернуть большой список одним ответом и проигнорировать параметр `start`. Скрипт видел более 50 строк, повторял запрос и мог бесконечно получать ту же страницу.

В новой версии:

- `methods` вызывается один раз;
- добавлена защита от повторяющейся страницы;
- добавлен максимальный лимит страниц;
- в Actions виден прогресс по каждому набору данных, страницам и batch-пакетам;
- сырые дубли REST-ответов по умолчанию отключены, поэтому запись на диск заметно быстрее;
- все нормализованные данные всё равно сохраняются в `json/datasets/`.

## Что выгружается

### Пользователи и структура

- пользователи и их исходные ID;
- подразделения;
- рабочие группы, проекты, Scrum и коллабы;
- задачи, ответственные, постановщики, соисполнители, наблюдатели, CRM-привязки и файловые ID;
- стадии канбана задач по группам и проектам;
- пользовательские поля задач и пользователей.

### CRM

- лиды;
- сделки;
- контакты;
- компании;
- реквизиты;
- адреса;
- банковские реквизиты;
- связи реквизитов;
- товарные позиции;
- связи сделка–контакт, лид–контакт и контакт–компания;
- CRM-дела;
- комментарии таймлайна;
- смарт-процессы, их поля, элементы и воронки.

### Все статусы и настройки полей

- `CRM_Status_Types` — полный перечень типов справочников `ENTITY_ID`;
- `CRM_Statuses` — стадии лидов, стадии всех воронок сделок, источники, типы, причины и другие CRM-справочники;
- `Deal_Categories` — все воронки сделок;
- `Task_Statuses` — системные статусы задач с ID и названиями;
- `Task_Stages` — стадии канбана задач по проектам и группам;
- `CRM_UserField_Config` — полная конфигурация пользовательских полей CRM, если webhook имеет нужные права;
- отдельные списки пользовательских полей лидов, сделок, контактов, компаний, реквизитов, задач и пользователей;
- `*.fields` — системные и пользовательские поля, используемые при выгрузке карточек.

Если отдельный метод недоступен по правам или тарифу, экспорт не останавливается: ошибка записывается в `Errors` и журнал выполнения.

## Запуск через GitHub Actions

1. Создайте приватный репозиторий.
2. Загрузите в корень содержимое этого архива.
3. Откройте `Settings → Secrets and variables → Actions`.
4. Создайте secret `BITRIX_WEBHOOK_URL`.
5. Вставьте полный URL входящего webhook администратора:

   `https://yourportal.bitrix24.kz/rest/USER_ID/TOKEN/`

6. Откройте `Actions → Export Bitrix24 to JSON and Excel → Run workflow`.
7. Оставьте включённым `include_history`, если нужны CRM-дела и комментарии таймлайна.
8. `save_raw_api` обычно оставляйте выключенным. Он создаёт вторую копию каждого ответа и только замедляет выгрузку.
9. После завершения скачайте artifact `bitrix24-dump-<номер запуска>`.

## Что будет видно в логе

Пример:

```text
[CRM_Statuses] начало: crm.status.list
CRM_Statuses: страница 1, получено 50, всего 50/137
CRM_Statuses: страница 3, получено 37, всего 137/137
[CRM_Statuses] готово: 137 строк за 2.4 сек.
```

Если Bitrix повторит ту же страницу, скрипт остановит пагинацию без добавления дублей и выведет предупреждение.

## Локальный запуск

```bash
cp .env.example .env
pip install -r requirements.txt
python -m pytest -q
python -u bitrix_export.py
```

## Важное ограничение

Это логический экспорт через REST API, а не физическая резервная копия базы облачного Bitrix24. Выгружается только то, что доступно пользователю webhook и открыто REST-методами. Исходные ID сохраняются, но в новой коробке ID пользователей, сущностей, стадий и файлов изменятся — при импорте понадобится таблица соответствий `старый ID → новый ID`.
