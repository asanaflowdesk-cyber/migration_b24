# Bitrix24 — рабочие автоматизации

Репозиторий содержит только действующие процессы коробочного Bitrix24. Разовый блок переноса CRM из облака удалён: workflows `01`, `10–13`, `processes/cloud_export` и `processes/cloud_to_box` больше не используются и в репозитории отсутствуют.

## Активные workflows

- `20 | Пользователи — регистрация из Google Sheets`
- `30 | e-Qazyna — ГПО в лиды`
- `31 | Пакеты учредителей — единый ответственный`
- `32 | Лиды — вернуть ошибочный провал в Новые`
- `33 | Исключённые пользователи — перенос пакетов`
- `34 | e-Qazyna — синхронизация статусов заявок`
- `35 | Обогащение компаний без руководителя`
- `36 | Компании — обновление данных из Google Sheets`
- `40 | FlowDesk → Bitrix24`
- `50 | Подразделения — массовое создание`

Основной secret для рабочих CRM-процессов:

```text
TARGET_BITRIX_WEBHOOK_URL
```

Для потоков, которые читают или записывают Google Sheets, также используется:

```text
GOOGLE_SERVICE_ACCOUNT_JSON
```

## Workflow 36 — обновление компаний из Google Sheets

Назначение: массово добавлять найденные телефоны, email, сайты и простые пользовательские поля в существующие компании Bitrix24.

Главные правила:

1. Компания определяется по `COMPANY_ID`; если его нет — по точному 12-значному БИН из `ORIGIN_ID/RQ_INN`.
2. Если одновременно указаны `COMPANY_ID` и БИН, БИН обязательно сверяется с карточкой и реквизитами.
3. `PHONE`, `EMAIL`, `WEB` только дополняются новыми уникальными значениями. Существующие контакты не стираются.
4. Пустая ячейка ничего не очищает.
5. `NAME/Название` используется только как контрольная подпись и не переименовывает компанию.
6. После `apply` карточка перечитывается из Bitrix24, и результат проверяется.
7. Поток пишет обратно в Google Sheets `STATUS`, `CHANGES`, `MESSAGE`, `BITRIX_COMPANY_ID`, `UPDATED_AT`.

Сначала запускать `dry_run`. Для реального обновления нужен `apply` и подтверждение:

```text
APPLY_COMPANY_UPDATES
```

Подробный формат таблицы: `processes/company_data_update/README.md`.

## Workflow 33 — перенос пакетов исключённых пользователей

Назначение: убрать остатки лидов с исключённых пользователей и привести связанный пакет к одному ответственному. Стадии лидов этот workflow **не меняет**.

Базовый список исключённых пользователей:

```text
15,17,19,22,23,39,44
```

Автоматические РОП для ещё не распределённых пакетов:

```text
72,73
```

Правила пакета:

1. Если определён учредитель — пакет объединяется по ФИО учредителя и связанным компаниям.
2. Если учредителя нет, но есть компания — `компания + её лиды` остаются полноценным сокращённым пакетом.
3. Если нет и компании — отдельный лид считается минимальным пакетом.
4. Лиды действующих пользователей не забираются; они используются только как контекст связей пакета.
5. Для пакетов с участием `16/18/38`: если остальных связанных лидов больше — пакет идёт РОПам `72/73`; иначе остатки переходят тому из `16/18/38`, у кого больше связанных лидов.
6. Все остальные пакеты целиком распределяются между `72` и `73` независимо от текущего владельца компании/контакта.
7. Балансировка идёт по количеству исходных лидов без дробления пакета.
8. Лид `401` защищён: пакет с ним не меняется автоматически.
9. Меняется только `ASSIGNED_BY_ID`. `STATUS_ID` и другие поля workflow 33 не трогает.

`dry_run` формирует один файл:

```text
excluded_user_reassignment.csv
```

`apply` выполняет тот же рассчитанный план, показывает прогресс `X/Y`, затем перечитывает CRM. Если после первой проверки остаются расхождения, workflow один раз повторяет только их внутри того же запуска и снова проверяет. Отдельного repair-workflow и отдельных plan/summary-файлов нет.

Для `apply` требуется подтверждение:

```text
REASSIGN_EXCLUDED_USERS
```
