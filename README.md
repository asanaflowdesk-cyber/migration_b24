# Миграция Bitrix24: облако → коробка

Репозиторий содержит код разового переноса данных из облачного Bitrix24 в коробку и отдельный, не связанный с миграцией, инструмент регистрации пользователей.

Готовый дамп облака зафиксирован в репозитории как контрольная точка:

```text
processes/cloud_to_box/input/bitrix24_dump_20260805_072425.zip
```

Основной источник каждого `dry_run` и `apply` — действующий облачный Bitrix24 через `SOURCE_BITRIX_WEBHOOK_URL`. Дамп используется только для сверки и как резерв по отдельному набору данных, если весь соответствующий метод облака временно недоступен. Excel из дампа предназначен для ручной проверки и не является источником миграции.

## Что переносится

Непосредственно из действующего облачного портала переносятся:

- 604 компании;
- 444 контакта;
- телефоны, email и связи контакт ↔ компания;
- 619 реквизитов и 1 160 адресов;
- 1 243 сделки с преобразованием в 1 233 лида и 10 сделок;
- 597 задач, включая завершенные;
- 134 CRM-дела, включая 57 незавершенных;
- ответственные, постановщики, исполнители, соисполнители и наблюдатели;
- подзадачи, чек-листы и комментарии задач;
- файлы задач, комментариев, чек-листов и CRM-дел;
- строгие связи задач и дел с компаниями, контактами, лидами и сделками;
- причины потери, детализация причины и номер договора из заполненных полей облака;
- технические карты старый ID → новый ID для возобновления и проверки импорта.

Четыре исходных тестовых лида не создаются. Их оставшиеся связи перенаправляются на сделки, в которые эти лиды были конвертированы.

## Правила воронки

В лиды переводятся сделки облака на стадиях:

- `NEW`;
- `UC_HRSCUK`;
- `UC_2DA5PB`;
- `UC_2Z4T64`;
- `UC_BF5JWI`;
- `EXECUTING` — стадия «В работе»;
- `LOSE` — все проваленные сделки, как закрытые некачественные лиды.

Сделками остаются:

- `FINAL_INVOICE`;
- `UC_9TWGUF`;
- `WON`.

Во все создаваемые лиды и сделки записывается:

```text
UF_CRM_1785917145255 = ГПО недропользователя
```

Перед записью код проверяет наличие поля в лидах и сделках и, для поля-списка, наличие соответствующего значения.

## Что не создается

- пользователи;
- подразделения и оргструктура;
- проекты и рабочие группы;
- Scrum, коллабы и смарт-процессы;
- товарные позиции.

Задачи из старых проектов создаются как обычные задачи с `GROUP_ID = 0`. Название, описание, статус, дедлайн, участники, подзадачи, чек-листы, комментарии, файлы и CRM-связи сохраняются.

## Сопоставление пользователей

Порядок сопоставления:

1. Ручное соответствие из `config/users.csv`, если оно задано.
2. Точное совпадение email.
3. Совпадение имени и фамилии без учета порядка слов, регистра, лишних пробелов и различия `ё/е`.

Неоднозначные совпадения не выбираются автоматически. Объекты, для которых не удалось сопоставить обязательного пользователя, не назначаются администратору и попадают в отчет ошибок.

Файл ручных соответствий:

```text
processes/cloud_to_box/config/users.csv
```

Формат:

```csv
source_user_id,target_user_id,comment
```

## Файлы и комментарии

Во время `dry_run` и реального импорта код читает из облака полные карточки компаний, контактов, лидов, сделок, реквизитов, адресов, задач и CRM-дел, а также их связи, комментарии, чек-листы и файлы.

`dry_run` строит те же целевые payload, что и реальный импорт, но не вызывает методы создания в коробке. Полное наполнение доступно в `preview_*.csv`, `full_transfer_preview.json`, `field_register.csv` и `relation_register.csv`.

Импорт возобновляемый: уже созданные карточки, задачи, дела, комментарии и файлы определяются по маркерам и картам ID и не создаются повторно. Для реальных запусков workflow 12 автоматически восстанавливает последнее сохраненное состояние из GitHub Actions Cache.

## GitHub Secrets

В `Settings → Secrets and variables → Actions` должны находиться:

```text
TARGET_BITRIX_WEBHOOK_URL
SOURCE_BITRIX_WEBHOOK_URL
```

- `TARGET_BITRIX_WEBHOOK_URL` — webhook коробки;
- `SOURCE_BITRIX_WEBHOOK_URL` — webhook облака для прямого чтения всех переносимых CRM-объектов, связей, задач, дел, комментариев и файлов.

Оба webhook должны иметь права на CRM, задачи и Диск. Для чтения чатов задач может потребоваться право на IM.

## Порядок запуска

Перед реальным переносом вручную отключить в коробке роботов, бизнес-процессы и массовые уведомления, которые могут сработать на создание карточек, задач или дел.

1. `10 | Миграция — проверить план`.
2. `11 | Миграция — сопоставить пользователей`.
3. Исправить все необходимые соответствия в `config/users.csv` и повторить поток 11.
4. `12 | Миграция — перенести данные в коробку`:
   - сначала `mode = dry_run`, `max_items = 0`;
   - затем `mode = apply`, `max_items = 10` для пробного реального пакета;
   - после проверки — `mode = apply`, `max_items = 0` для полного переноса.
5. `13 | Миграция — сверить результат`.

Для режима `apply` требуется подтверждение:

```text
IMPORT_FULL_CLOUD_DUMP
```

Каждый поток сохраняет Artifact с файлами:

- `actions.csv`;
- `errors.csv`;
- `maps.json`;
- `summary.json`.

## Отдельный поток регистрации пользователей

Поток `20 | Пользователи — регистрация из Excel` не участвует в миграции и сейчас запускать его не нужно.

## Постоянный парсер e-Qazyna

Поток `30 | e-Qazyna — ГПО в лиды` работает через тот же разрешенный Windows self-hosted runner и использует секрет коробки `TARGET_BITRIX_WEBHOOK_URL`.

Парсер:

- создаёт и обновляет только лиды;
- не создаёт компании, контакты, сделки, пользователей, подразделения, проекты или группы;
- поддерживает один основной лид на один БИН;
- новые заявки того же БИН дописывает в существующий лид и его таймлайн;
- не возвращает существующий лид на начальную стадию;
- не меняет текущего ответственного при обновлении;
- записывает `UF_CRM_1785917145255 = ГПО недропользователя`;
- после миграции распознаёт старые маркеры `EQAZYNA / eQazyna|номер|БИН` и переводит выбранный лид на постоянный маркер `EQAZYNA_LEAD / БИН`, чтобы не создавать ещё один дубль;
- имеет `dry_run`, который проверяет поле, доступ к коробке и план действий без записи;
- для `apply` требует подтверждение `IMPORT_EQAZYNA_LEADS`.

Код находится в:

```text
processes/eqazyna_leads/
```

Для обогащения через data.egov.kz используется необязательный secret:

```text
EGOV_API_KEY
```

Поток запускается вручную. Автоматическое расписание в репозиторий не добавлено.
