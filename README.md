# Миграция Bitrix24: облако → коробка

Репозиторий содержит разовую миграцию данных из облачного Bitrix24 в коробку и отдельные вспомогательные процессы. Боевой перенос сделан fail-closed: необъяснённый `ERROR`, потеря обязательной связи, несопоставленный обязательный пользователь, повреждённый дамп или провал итоговой проверки завершают запуск ошибкой.

## Источник миграции

Основной источник core-данных для production `apply` — неизменяемый дамп:

```text
processes/cloud_to_box/input/bitrix24_dump_20260805_072425.zip
```

В `config/migration.json` закреплён `source_mode = dump`. Production `apply` с `source_mode = live` запрещён, потому что последовательные REST-чтения живого портала не образуют атомарный снимок.

`SOURCE_BITRIX_WEBHOOK_URL` всё ещё нужен во время импорта для проверки доступа и дочитывания дочернего контента, который отсутствует/неполон в дампе: комментариев задач, чек-листов, файлов и отдельных live-привязок. Эти дочерние данные имеют явно описанную best-effort политику; core-сущности и core-связи — блокирующие.

Перед первой записью приложение проверяет manifest дампа, SHA-256 и количество строк каждого набора.

## Что переносится

Контрольная точка содержит:

- 604 компании;
- 444 контакта;
- телефоны, email и связи контакт ↔ компания;
- 619 реквизитов;
- 1 160 исходных строк адресов, из которых 907 уникальных адресных payload переносятся после детерминированной дедупликации;
- 1 243 исходные сделки с преобразованием в 1 233 лида и 10 сделок;
- 597 исходных задач, из которых 8 исключены утверждённой конфигурацией участников; ожидаемый перенос — 589 задач, включая завершённые;
- 134 CRM-дела, включая 57 незавершённых;
- ответственные, постановщики, исполнители, соисполнители и наблюдатели;
- подзадачи, чек-листы и комментарии задач;
- файлы задач, комментариев, чек-листов и CRM-дел;
- связи задач и дел с компаниями, контактами, лидами и сделками;
- причины потери, детализация причины и номер договора из заполненных полей облака;
- технические карты старый ID → новый ID и identity-manifest состояния.

Четыре исходных тестовых лида не создаются. Для них в конфигурации закреплена явная карта converted lead → deal; сопоставление по изменяемому `TITLE` не используется.

В исходном snapshot есть две подтверждённые сиротские ссылки deal → company: `668 → 382` и `1344 → 730`. Отсутствующие компании не выдумываются. Эти два известных исключения закреплены в allowlist целостности: сделки переносятся без несуществующей связи с компанией, а исключение отражается в отчёте.

## Правила воронки

В лиды переводятся сделки облака на стадиях:

- `NEW`;
- `UC_HRSCUK`;
- `UC_2DA5PB`;
- `UC_2Z4T64`;
- `UC_BF5JWI`;
- `EXECUTING` — стадия «В работе»;
- `LOSE` — проваленные сделки как закрытые некачественные лиды.

Сделками остаются:

- `FINAL_INVOICE`;
- `UC_9TWGUF`;
- `WON`.

Продукт «ГПО недропользователя» записывается в разные поля целевых сущностей:

```text
Лид:    UF_CRM_1785917145255
Сделка: UF_CRM_6A73073A5405E
```

Перед записью проверяются наличие поля и допустимое значение списка.

## Защита от дублей и повреждения целевого портала

- автоматический merge разрешён только для карточек с одинаковым точным migration marker;
- БИН, ФИО, телефон и email могут использоваться только как кандидаты для анализа, но не для автоматического разрушительного merge;
- изменяющие POST-запросы после неоднозначного timeout/connection reset автоматически не повторяются;
- повторный запуск сначала сверяет существующие migration markers и текущие связи;
- связи контакт ↔ компания, лид ↔ контакт и сделка ↔ контакт добавляются через `*.add`; `*.items.set`, заменяющий весь набор связей, не используется;
- вручную добавленные в коробке CRM-связи не удаляются и не перезаписываются миграцией;
- состояние `maps.json` принимается только вместе с совпадающим `state_manifest.json`, привязанным к source snapshot, конфигурации, карте пользователей и target portal.

## Что не создаётся

- пользователи;
- подразделения и оргструктура;
- проекты и рабочие группы;
- Scrum, коллабы и смарт-процессы;
- товарные позиции.

Задачи из старых проектов создаются как обычные задачи с `GROUP_ID = 0`. Название, описание, статус, дедлайн, участники, подзадачи, чек-листы, комментарии, файлы и CRM-связи сохраняются в пределах поддерживаемых REST-методов.

## Сопоставление пользователей

Порядок:

1. ручное соответствие из `config/users.csv`;
2. точное совпадение email;
3. совпадение имени и фамилии без учёта порядка слов, регистра, лишних пробелов и `ё/е`.

Неоднозначные совпадения не выбираются автоматически. При несопоставленном обязательном пользователе strict-preflight блокирует импорт.

Файл ручных соответствий:

```text
processes/cloud_to_box/config/users.csv
```

Формат:

```csv
source_user_id,target_user_id,comment
```

## Dry-run, отчёты и верификация

`dry_run` строит план целевых payload и проверяет конфигурацию/доступы, но не является доказательством того, что коробка примет каждый изменяющий запрос: ограничения API, права, роботы и фактическая серверная валидация полностью проверяются только на тестовом `apply`.

Отчёты по умолчанию санитизируются: webhook URL, телефоны, email и свободный текст с ПДн не должны попадать в обычные Actions artifacts. Полные чувствительные preview-файлы создаются только при явном локальном opt-in `B24_REPORT_SENSITIVE_PAYLOADS=1`; в GitHub workflow эта опция не включена.

`verify` возвращает ненулевой exit code при gap/mismatch и проверяет не только количества маркеров, но и ключевые поля и CRM-связи source → target.

## GitHub Secrets и variables

Обязательные secrets для миграции:

```text
TARGET_BITRIX_WEBHOOK_URL
SOURCE_BITRIX_WEBHOOK_URL
```

- `TARGET_BITRIX_WEBHOOK_URL` — webhook коробки;
- `SOURCE_BITRIX_WEBHOOK_URL` — webhook облака для preflight и дочернего контента задач/файлов.

Webhook должны иметь минимально необходимые права CRM, задач и Диска; для чтения чатов задач может потребоваться IM. Реальные webhook нельзя хранить в `.env`, репозитории или артефактах. Для локального запуска используйте `.env.example` как шаблон и храните рабочий `.env` только локально.

## Порядок запуска миграции

Перед записью в коробку вручную отключить роботов, бизнес-процессы и массовые уведомления, которые могут сработать на создаваемые карточки.

1. `00 | CI — код и тесты` должен быть зелёным.
2. `10 | Миграция — проверить план`.
3. `11 | Миграция — сопоставить пользователей`.
4. Исправить обязательные соответствия в `config/users.csv` и повторить шаг 11.
5. `12 | Миграция — перенести данные в коробку`:
   - `mode = dry_run`, `max_items = 0`;
   - `mode = apply`, `max_items = 10` на тестовой/контролируемой коробке;
   - `13 | Миграция — сверить результат`;
   - после проверки — `mode = apply`, `max_items = 0`;
   - снова workflow 13.
6. Только после зелёной итоговой сверки включать штатные роботы коробки.

Для `apply` требуется подтверждение:

```text
IMPORT_FULL_CLOUD_DUMP
```

Поток 12 не восстанавливает произвольный «последний cache» GitHub Actions. Повторный запуск безопасно сверяется по migration markers; локальное состояние валидируется по identity-manifest и не принимается для другого snapshot/config/target.

Artifacts хранятся 3 дня. Raw API export в workflow 01 создаётся только по отдельному ручному флагу и хранится 1 день.

## Приватные входные данные

Архив для передачи содержит текущий дамп и Excel, чтобы оставаться самодостаточным. `.gitignore` намеренно запрещает новый commit `*.zip`, `*.xlsx` и `processes/*/input/*`. Перед публикацией репозитория входные файлы с ПДн следует вынести в защищённое хранилище/секретный артефакт организации.

## Вспомогательные процессы

- `01 | Облако — экспорт` — read-only экспорт snapshot;
- `20 | Пользователи — регистрация из Excel` — отдельный процесс, не часть миграции;
- `30 | e-Qazyna — ГПО в лиды` — постоянный парсер;
- `31 | Компании — ответственный по руководителю компании` — сверка/коррекция только `ASSIGNED_BY_ID` компании;
- `32 | Лиды — вернуть ошибочный провал в Новые` — контролируемое восстановление лидов;
- `33 | e-Qazyna — синхронизация статусов заявок` — точная сверка существующих e-Qazyna лидов по номеру заявки: `Отклонено` / `Отозвано` / `Аннулировано` → `Провал`, `Выдана лицензия` → `Потенциальные сделки`;
- `40 | FlowDesk` — создание задач по входному событию с event-marker идемпотентности;
- `50 | Подразделения` — отдельный процесс создания подразделений.

Подробности каждого вспомогательного процесса находятся в его каталоге.
