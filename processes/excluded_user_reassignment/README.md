# Переназначение пакетов исключённых пользователей

Основной workflow: `33 | Исключённые пользователи — переназначить все лиды`.
Для добора после частично выполненного переноса используется `34 | Перенести остатки пакетов исключённых пользователей`.

Текущий набор для workflow 34 зафиксирован так:

- исключённые пользователи: `15,17,19,22,23,39,44`;
- целевые РОПы: `72,73`;
- защищённые пользователи, которых нельзя трогать: `13,16,18,38,40,58`;
- защищённый лид: `401`;
- каждый переносимый лид должен получить целевого РОПа и `STATUS_ID = NEW`.

## Правила пакетов

1. Исходный охват строится **по текущему состоянию CRM**, а не по старому CSV-плану. В обработку попадают только лиды, которые на момент запуска всё ещё закреплены за исключёнными пользователями.
2. Пакет строится по учредителю/руководителю, если он определён по `CONTACT_ID` и ФИО. Один учредитель и связанные с ним компании/лиды не делятся между РОПами.
3. Если учредитель отсутствует, это **не ошибка и не причина пропуска**. При наличии компании создаётся сокращённый пакет `компания + все выбранные лиды этой компании`. Если отсутствует и компания, лид остаётся самостоятельным однолидовым пакетом.
4. Остаточный запуск идемпотентен. Если часть пакета уже перенесена на РОПа `72` или `73`, этот РОП не считается «чужим владельцем»: весь оставшийся пакет закрепляется за тем же РОПом. Это устраняет самоблокировку повторного запуска.
5. Если внутри одного пакета уже одновременно присутствуют оба целевых РОПа `72` и `73`, пакет автоматически не склеивается и уходит в отчёт `skipped_conflicting_target_rops`.
6. Если в пакете есть владелец вне исключённых пользователей и вне целевых РОПов, пакет не трогается целиком (`skipped_existing_owner`). Так сохраняются лиды менеджеров `13,16,18,38,40,58` и любые другие реально действующие закрепления.
7. Лид `401` никогда не включается в исходный перенос и фиксируется как `skipped_protected_lead`, если всё ещё находится у исключённого пользователя.
8. Пакеты, связанные с ответственным из подразделения Талдыкоргана, автоматически не переносятся (`skipped_taldykorgan`). Филиал определяется по `UF_DEPARTMENT` ответственного, а не по адресу компании.
9. Новые, ещё не начатые пакеты балансируются между `72` и `73` по количеству лидов. Пакеты, уже частично закреплённые за одним из этих РОПов, продолжаются у этого же РОПа и не перебалансируются.
10. Для лида `ASSIGNED_BY_ID` и `STATUS_ID = NEW` записываются **одним `crm.lead.update`**. После паузы выполняется контрольное чтение; если робот Bitrix24 вмешался, целевое состояние записывается повторно и затем проверяется ещё раз.

## Отчёты

- `excluded_user_reassignment.csv` — фактический план/результат переноса;
- `excluded_user_reassignment_warnings.csv` — неполные связи (нет учредителя/компании), которые теперь обрабатываются сокращёнными пакетами, а не пропускаются;
- `excluded_user_reassignment_skipped.csv` — только реально защищённые или неоднозначные пакеты;
- `excluded_user_reassignment_summary.json` — итоговые счётчики.

`dry_run` ничего не меняет. Для workflow 33 боевой запуск подтверждается `REASSIGN_EXCLUDED_USERS`. Для workflow 34 — `TRANSFER_REMAINING_PACKAGES`.
