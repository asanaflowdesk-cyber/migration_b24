# Lead recovery

Ручной сервисный поток для возврата ошибочно закрытых лидов.

Правило выборки:
- лид сейчас находится в провальной стадии (`STATUS_SEMANTIC_ID = F`);
- в текущую провальную стадию его перевёл заданный пользователь (`MOVED_BY_ID`);
- перевод выполнен за последние N дней по `MOVED_TIME` (по умолчанию 7 дней).

Действие:
- `STATUS_ID` меняется на `NEW`;
- поле причины провала `UF_CRM_1785508658316` очищается;
- исходный `ASSIGNED_BY_ID` передаётся в update явно, чтобы сохранить текущего исполнителя;
- после массового перевода поток ждёт 12 секунд, чтобы успели отработать роботы стадии `NEW`;
- если робот успел сменить исполнителя или вернуть причину провала, поток восстанавливает исходного исполнителя и повторно очищает причину;
- после ремонта выполняется финальная повторная проверка;
- если стадия, исполнитель или причина всё равно не соответствуют требованию, поток завершается с ошибкой и пишет лид в отчёт.

По умолчанию workflow запускается в `dry_run`. Для боевой записи требуется `apply` и подтверждение `RESTORE_FAILED_LEADS`.

ID пользователя определяется безопасно: сначала из input `moved_by_id`, затем из repository variable `LEAD_RECOVERY_MOVED_BY_ID`. Вызов `user.current` не используется, поэтому CRM-only webhook не требует дополнительного user scope. Если ID не задан ни одним способом, поток останавливается до любых изменений.

Для HTTP timeout workflow передаёт значение в `HTTP_TIMEOUT_SECONDS`, которое действительно читает общий `BitrixClient`.
