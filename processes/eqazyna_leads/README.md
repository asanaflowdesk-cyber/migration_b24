# e-Qazyna Minerals -> лиды коробочного Bitrix24

Процесс выполняется на том же Windows self-hosted runner, что и миграция. Он читает e-Qazyna Minerals, обогащает записи через data.egov.kz и создаёт полный комплект связанных CRM-сущностей в коробке.

## Правила

- один БИН = один лид;
- новый лид создаётся на стадии `NEW`;
- стадия и ответственный существующего лида не сбрасываются;
- название лида формируется по правилам миграции: `ТОО Название. e-Qazyna № 42468-NEA`;
- длинные организационно-правовые формы сокращаются до `ТОО`, `ИП`, `АО`, `ЧК` и т.д.;
- одна компания создаётся или находится по `ORIGINATOR_ID=EQAZYNA`, `ORIGIN_ID=БИН` и реквизиту `RQ_BIN`;
- к компании создаётся или обновляется реквизит с БИН, полным названием, директором, ОКЭД и юридическим адресом;
- при наличии полноценного ФИО создаётся или находится контакт руководителя и связывается с компанией и лидом;
- пустые контакты `Руководитель` без нормального ФИО не создаются;
- новая заявка того же БИН добавляется в комментарии и таймлайн существующего лида;
- в поле `UF_CRM_1785917145255` записывается точное значение `ГПО Недропользователя`;
- лид получает `ORIGINATOR_ID=EQAZYNA_LEAD`, `ORIGIN_ID=БИН`;
- сделки не создаются;
- `dry_run` читает коробку и показывает план создания/обновления, но не выполняет запись ни в одну CRM-сущность.

## Запуск

В GitHub Actions открыть поток `30 | e-Qazyna — ГПО в лиды`.

1. Первый запуск: `mode=dry_run`, одна страница.
2. Проверить в журнале ID лида, компании, контакта и реквизита.
3. Для записи выбрать `mode=apply` и ввести `IMPORT_EQAZYNA_LEADS`.

## Секреты

- `TARGET_BITRIX_WEBHOOK_URL` — webhook коробочного Bitrix24;
- `EGOV_API_KEY` — обязательный ключ data.egov.kz.

## Переменные репозитория

- `BITRIX_ASSIGNED_BY_ID` — ответственный для новых лидов/компаний/контактов;
- `BITRIX_REQUISITE_PRESET_ID` — шаблон реквизитов компании; по умолчанию `1`; при наличии перенесённых реквизитов фактический PRESET_ID определяется по ним, поэтому устаревшая переменная `3` не блокирует запуск;
- `PIP_INDEX_URL`, `BITRIX_CA_BUNDLE`, `BITRIX_VERIFY_SSL` — технические настройки runner.

## Совместимость с миграцией

Перенесённые компании уже имеют:

```text
ORIGINATOR_ID = EQAZYNA
ORIGIN_ID = БИН
```

Перенесённые реквизиты имеют `RQ_BIN=БИН` и `XML_ID=EQAZYNA-REQ-БИН`. Парсер сначала ищет их и обновляет, а не создаёт дубли.

Старые облачные заявки после миграции могут иметь маркер:

```text
ORIGINATOR_ID = EQAZYNA
ORIGIN_ID = eQazyna|номер заявки|БИН
```

Парсер находит такой лид по БИН, связывает его с компанией, контактом и реквизитами и переводит на постоянный маркер `EQAZYNA_LEAD / БИН`.
