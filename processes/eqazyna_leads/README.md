# e-Qazyna Minerals -> лиды коробочного Bitrix24

Процесс выполняется на том же Windows self-hosted runner, что и миграция. Он читает e-Qazyna Minerals, обогащает записи через data.egov.kz и создаёт связанный комплект CRM-сущностей в коробке.

## Основные правила

- одна заявка e-Qazyna = один лид;
- дубль определяется по точному номеру заявки, например `47408-NEA`;
- если заявка с таким номером уже есть в `ORIGIN_ID`, названии или комментарии лида, она полностью пропускается;
- разные заявки одной компании создают разные лиды;
- одна компания и один реквизит используются совместно для всех заявок одного БИН;
- при наличии полноценного ФИО создаётся или находится контакт руководителя;
- лид связывается с компанией и контактом руководителя;
- сделки не создаются.

## Сопоставление eGov

Надёжным считается результат, когда:

- БИН совпал точно;
- сходство названия e-Qazyna и eGov не ниже 60%.

ОКЭД используется как информационное поле и не блокирует обогащение.

## Название лида

Название формируется по правилам миграции:

```text
ТОО Название. e-Qazyna № 47408-NEA
```

Длинные организационно-правовые формы сокращаются до `ТОО`, `ИП`, `АО`, `ЧК` и т.д.

## Стадия нового лида

Парсер ищет последний лид, связанный:

1. с контактом руководителя;
2. с компанией;
3. с БИН — для старых карточек без нормальных связей.

Из найденных карточек выбирается фактически самая поздняя по `DATE_MODIFY`, затем по ID.

Правило теперь однозначное:

- каждая новая заявка создаётся на стадии `NEW`, даже если предыдущий связанный лид был провален;
- причины `Не дозвонились`, `Клиент отказался`, `Не подходит по критериям` и любые другие причины прошлого провала не наследуются;
- единственное исключение — последний связанный лид закрыт как неудачный с причиной `Уже работает с Евразией`; в этом случае новая заявка создаётся в `JUNK` и получает эту причину;
- никакая другая историческая стадия не наследуется: даже если старый провал был в кастомной неудачной стадии, новая заявка идёт в `NEW`;
- причина может приходить из Bitrix24 как текст, ID или одноэлементный список; парсер распознаёт варианты по метаданным поля и при записи enum использует ID значения.

## Назначение ответственного

В распределении участвуют только пользователи:

```text
22 — Гаухар Джунисалиева
23 — Айнура Жумакан
16 — Андрей Крижевский
17 — Юлия Сидикова
18 — Ксения Кудайбергенова
38 — Асет Исаев
44 — Алина Курбанова
39 — Владимир Петухов
40 — Еркебулан Толекбергенов
19 — Алия Казрахметова
15 — Ольга Скребцова
```

Правило назначения однозначное:

1. если карточка контакта руководителя уже существует и в ней указан ответственный из утверждённого списка, этот менеджер назначается новому лиду;
2. ответственные прошлых лидов и карточки компании для назначения не используются;
3. если контакт создаётся впервые, у него нет ответственного либо ответственный не входит в утверждённый список, выполняется случайный выбор среди менеджеров с минимальным количеством незакрытых лидов.

Таким образом, единственный источник исторического закрепления — поле `ASSIGNED_BY_ID` в карточке контакта руководителя. Пользователь вне утверждённого списка игнорируется.

При первичном распределении:

- для каждого менеджера считается количество незакрытых лидов;
- определяется минимальная загрузка;
- если минимум одинаковый у нескольких менеджеров, один из них выбирается случайно;
- выбранный менеджер назначается новому лиду, новой компании и новому контакту;
- существующая компания парсером никогда не переназначается; ее ответственный сверяется отдельным workflow `31 | Компании — ответственный по первому лиду`;
- существующий контакт без допустимого ответственного может быть переведен на выбранного менеджера, так как именно контакт является источником закрепления для новых лидов;
- внутри одного запуска плановая загрузка увеличивается после каждой назначенной заявки, поэтому следующие заявки распределяются с учётом уже запланированных лидов.

## Компания, контакт и реквизит

Компания ищется по:

```text
ORIGINATOR_ID = EQAZYNA
ORIGIN_ID = БИН
```

и по БИН в реквизитах.

Контакт руководителя ищется внутри компании по ФИО. Пустые значения `Руководитель`, `Директор`, `Не найден` и ФИО из одного слова не создают контакт.

Реквизит принадлежит компании, а не лиду. В него записываются БИН, полное и краткое название, руководитель, ОКЭД и юридический адрес. Ошибка реквизита или адреса фиксируется как предупреждение и не отменяет создание лида.

## Поля лида

```text
ORIGINATOR_ID = EQAZYNA_LEAD
ORIGIN_ID = номер заявки
STATUS_ID = NEW; исключение — JUNK только для причины «Уже работает с Евразией»
UF_CRM_1785508658316 = заполняется только для указанного исключения (ID значения списка)
UF_CRM_1785917145255 = ГПО Недропользователя
```

Также записываются `COMPANY_ID`, `CONTACT_ID`, `ASSIGNED_BY_ID`, название, БИН, адрес, руководитель, ОКЭД, дата и статус заявки, ссылка e-Qazyna и данные eGov.

## Режимы запуска

`dry_run` читает e-Qazyna, eGov и Bitrix24, рассчитывает стадию, причину, ответственного и действия по сущностям, но ничего не записывает.

`apply` выполняет создание и обновление. Для боевого запуска требуется подтверждение:

```text
IMPORT_EQAZYNA_LEADS
```

## Результаты

Формируются:

```text
eqazyna_bitrix_leads.xlsx
eqazyna_bitrix_leads.json
eqazyna_bitrix_leads_pages.json
```

В отчёте отражаются правило назначения, выбранный менеджер, стадия, причина исключения и ID связанного лида, использованного для проверки истории.
