# e-Qazyna Minerals → лиды коробочного Bitrix24

Процесс выполняется на том же Windows self-hosted runner, что и миграция. Он читает реестр e-Qazyna Minerals и работает только с лидами коробочного Bitrix24.

## Правила

- один БИН поддерживается как один лид;
- компании, контакты, реквизиты и сделки не создаются;
- новая заявка того же БИН добавляется в комментарии и таймлайн существующего лида;
- стадия и ответственный существующего лида не сбрасываются;
- в поле `UF_CRM_1785917145255` всегда записывается `ГПО недропользователя`;
- новые лиды получают `ORIGINATOR_ID=EQAZYNA_LEAD`, `ORIGIN_ID=БИН`;
- `dry_run` подключается к коробке, проверяет поле и читает лиды, но не вызывает `crm.lead.add` и `crm.lead.update`.

## Запуск

В GitHub Actions открыть поток `30 | e-Qazyna — ГПО в лиды`.

1. Первый запуск: `mode=dry_run`, одна страница.
2. Проверить журнал и при необходимости скачать artifact.
3. Для записи выбрать `mode=apply` и ввести `IMPORT_EQAZYNA_LEADS`.

## Секреты

- `TARGET_BITRIX_WEBHOOK_URL` — webhook коробочного Bitrix24;
- `EGOV_API_KEY` — ключ data.egov.kz. Без него лиды всё равно обрабатываются, но без доверенного обогащения eGov.

## Переменные репозитория

Необязательные: `BITRIX_ASSIGNED_BY_ID`, `PIP_INDEX_URL`, `BITRIX_CA_BUNDLE`, `BITRIX_VERIFY_SSL`.

## Совместимость с разовой миграцией

Старый облачный парсер сохранял заявки как отдельные сделки с маркерами:

```text
ORIGINATOR_ID = EQAZYNA
ORIGIN_ID = eQazyna|номер заявки|БИН
```

После переноса такие записи становятся лидами. Новый парсер сначала ищет постоянный маркер `EQAZYNA_LEAD / БИН`, затем ищет старые мигрированные маркеры, содержащие тот же БИН. Найденный лид переводится на постоянный маркер. Это предотвращает создание дополнительного лида сразу после разовой миграции.
