# Пакет учредителя ГПО недропользователя

Для пакета, вышедшего с ID 4, источник — сохранённое первое назначение.
Для остальных пакетов источник — контакт, связанный с лидом через `CONTACT_ID`.
Остальные контакты, компании и все их лиды получают его текущий
`ASSIGNED_BY_ID`. Лиды без компании, связанные с контактами пакета, тоже
включаются. Стадии и статусы не меняются.

## Первое назначение пакета с ID 4

ID 4 — техническая очередь. Первое зафиксированное назначение любого элемента
пакета на сотрудника закрепляет за ним весь пакет: контакты, компании и все
связанные лиды. Назначение нового лида на другого сотрудника это закрепление
не меняет — лид и остальные расхождения возвращаются первому менеджеру.
То же правило защищает закрепление при изменении компании или контакта.

Пример: все карточки на ID 4 → лид А назначен ID 13 → пакет закреплён за 13 →
новый лид Б назначен ID 14 → лид Б переносится на ID 13.

Закрепление сохраняется **до записи в CRM** в `first_assignment.sqlite3`
в папке состояния worker, вне runtime. Перезапуск и push исходников его не
сбрасывают. Ошибка переноса не разрешает выбрать следующего менеджера.
`dry_run` показывает решение, не создавая и не меняя постоянное закрепление.
Пакеты без учредителя обрабатываются как компания с лидами, а без компании —
как контакт с лидами либо отдельный лид. Противоречивые связи ФИО не обходятся
переходом к сокращённому пакету.

Порядок назначений хранится в отдельном листе `OWNER_EVENTS` Google-очереди.
События не схлопываются до последнего владельца. Порядок определяется временем
события Б24; при одинаковом времени — последовательностью регистрации.
После сохранения первого назначения более поздние события не меняют владельца.
Не удаляйте и не переставляйте строки `OWNER_EVENTS`, а также не удаляйте файл
закреплений worker: это история, необходимая для восстановления порядка.

Если события недоступны, периодическая сверка может восстановить назначение,
когда виден только один сотрудник. Если до первой фиксации уже есть несколько
разных сотрудников и порядок не сохранён, пакет попадает в отчёт с
`first_assignment_order_unknown`, без выбора по ID или дате последней правки.

Роботу Б24 достаточно назначить сотрудника в лиде, компании **или** контакте.
Скрипт сам перенесёт назначение в остальные карточки, включая контакт учредителя.
В `output/recovery.json` раздел `first_assignments` показывает менеджера,
первый элемент и способ фиксации назначения.

### Включение новой логики

1. Обновить `integrations/bitrix_owner_sync_queue/Code.gs`, запустить `setupQueue`
   и опубликовать новую версию существующего Apps Script web app с тем же URL.
   Старые листы `QUEUE`, `TRANSFER_LOG` и `TRANSFER_ITEMS` сохраняются; добавится
   лист `OWNER_EVENTS`.
2. Опубликовать обновлённый обработчик из `integrations/bitrix_owner_sync_webhook`.
   В его серверном окружении рекомендуется задать `TARGET_BITRIX_WEBHOOK_URL`
   для чтения ответственного, если в событии робота нет OAuth-токена.
3. Повторно открыть страницу установки приложения `/api/bitrix/install` в Б24.
   Она зарегистрирует `ADD` и `UPDATE` для контактов, компаний и лидов.
4. Обновить код репозитория и перезапустить worker действием `restart` потока 31A.
   Статусы и стадии карточек новая логика не меняет.

До обновления внешних обработчиков работает периодическая сверка с описанным
выше ограничением восстановления порядка. Один push в GitHub сам по себе
не публикует Apps Script и обработчик событий.

## Связи и источник

Контакты распознаются по «руководитель», «учредитель», «директор» в должности
либо метке `EQAZYNA_DIRECTOR` в комментариях без учёта регистра. ФИО
нормализуется; разные отчества и противоречащие друг другу связи компаний
не объединяются автоматически. Компания включается по связи с контактом,
связи через лид или совпадению ФИО с `RQ_DIRECTOR` реквизита.

Дата изменения карточки не определяет источник. Дубль без связи с лидом
не может вернуть пакет на РОПа, если в пакете есть связанный контакт.

Для пакетов без первого закрепления после принятия корректного события ID источника сохраняется до записи в CRM в `authority_sources.json`
вне runtime и остаётся после перезапуска. Без сохранённого источника связанные
с лидами контакты должны иметь одного ответственного. Разные ответственные
означают конфликт. Если сохранённый источник больше не связан с лидом, пакет
пропускается до исправления связи или нового корректного события.

## Worker и восстановление

`31A | Founder package worker control` управляет постоянным worker на Windows.
События хранятся в Google Apps Script очереди; Action не запускается на каждое
событие. Worker читает журнал назначений, обрабатывает очередь контактов и
сверяет CRM при новых событиях назначения, старте и периодически через
`OWNER_SYNC_RECOVERY_SECONDS` (по умолчанию 300 секунд).
Это исправляет пакеты при потерянном событии или поздней записи другого процесса.

Ответственный источника перечитывается перед записью и после неё. Результат
записи проверяется чтением. Смена источника вызывает повторную сверку; ошибка
оставляет пакет `PARTIAL`, который повторяется в следующем проходе. Совпадающие
карточки не обновляются. Последний результат: `output/recovery.json`.
Перед изменением контактов регистрируется подавление собственных событий в
очереди, чтобы автоматическая запись дубля не меняла выбранный источник.

Push изменений worker в `main` запускает тесты, перезапуск и ожидание свежего
отчёта сверки. В логе — сводка и ID источников изменённых пакетов.
Ручные команды: `start`, `stop`, `restart`, `status`.
Workflow 31 выполняет ручную сверку по той же логике, по умолчанию `dry_run`.
Отчёт: `company_lead_owner_reconcile.xlsx`.

## Внешние обработчики

Код обработчика: `integrations/bitrix_owner_sync_webhook/`.
Код очереди: `integrations/bitrix_owner_sync_queue/Code.gs`.
Кэш ответственного обновляется после сохранения задания, чтобы сбой записи
не превращал повтор события в `owner_unchanged`.

Apps Script требует отдельной публикации новой версии web app; push в GitHub
её не публикует. Сверка worker восстанавливает остатки и со старой очередью.
