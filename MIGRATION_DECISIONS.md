# Зафиксированные решения по переносу — актуальная версия 2026-09-10

1. Production `apply` использует неизменяемый snapshot (`source_mode=dump`); live REST не считается атомарным источником core-данных.
2. `SOURCE_BITRIX_WEBHOOK_URL` используется для preflight и дочернего контента, которого нет в snapshot; ошибки core-данных блокируют запуск.
3. Пользователи, подразделения, проекты и рабочие группы миграцией не создаются.
4. Пользователи сопоставляются по ручной карте, затем email, затем ФИО без учёта порядка/регистра/`ё-е`; неоднозначность не разрешается автоматически.
5. Четыре исходных тестовых лида не создаются; их converted lead → deal соответствия закреплены явными source ID в `migration.json`.
6. Все проваленные исходные сделки становятся закрытыми лидами; стадия «В работе» также маршрутизируется в лид.
7. Из 1 243 исходных сделок формируется 1 233 лида и 10 сделок.
8. Продукт «ГПО недропользователя» записывается в `UF_CRM_1785917145255` у лидов и `UF_CRM_6A73073A5405E` у сделок.
9. В snapshot 597 задач; 8 задач с утверждёнными исключёнными участниками не переносятся. Ожидаемый итог — 589 задач.
10. Задачи старых проектов создаются без проекта/рабочей группы (`GROUP_ID=0`).
11. Сохраняются участники, иерархия подзадач, чек-листы, комментарии, вложения и CRM-связи в пределах поддерживаемых REST-возможностей.
12. Переносятся 134 CRM-дела, включая 57 незавершённых.
13. 1 160 raw address rows детерминированно дедуплицируются до 907 уникальных адресных payload.
14. Две известные source-orphan связи `deal 668 → company 382` и `deal 1344 → company 730` не «чинятся» вымышленными компаниями; сделки создаются без отсутствующей связи, исключение журналируется.
15. CRM-даты создания/изменения и полная история стадий не подделываются, если REST API не позволяет их восстановить.
16. При невозможности восстановить исходного автора/дату комментария метаданные фиксируются текстом, а не подменяются другой учётной записью без следа.
17. Любой необъяснённый `ERROR`, обязательный gap, обязательный unmapped user или mismatch `verify` делает запуск неуспешным.
18. Автоматический merge разрешён только для точного одинакового migration marker. БИН, ФИО, телефон и email не являются достаточным основанием для автоматического merge.
19. Изменяющие POST-запросы после неоднозначного сетевого сбоя автоматически не повторяются. Повторный run выполняет reconciliation по marker/текущему состоянию.
20. CRM relation import использует additive `*.add`; полный `*.items.set` запрещён, чтобы не удалять ручные target-only связи.
21. `maps.json` используется только с совпадающим `state_manifest.json`, привязанным к snapshot/config/users/target portal; повреждённое или чужое состояние отклоняется.
22. Excel из snapshot остаётся человекочитаемой сверкой, но не является source-of-truth миграции.
23. Dry-run строит максимально полный план, но не объявляется эквивалентом реального server-side `apply`.
24. Обычные отчёты санитизируются; чувствительные full-payload preview допускаются только локально по явному opt-in и не включены в GitHub workflow.
